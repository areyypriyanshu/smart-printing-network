# ADR 033: Queue-wait estimates stay rule-based; simulated data cannot justify ML

Date: 2026-10-24
Status: Accepted
Requirement: FR-31, FR-33 and FR-34, Sprint 9

## Context

Customers need a useful idea of how busy a shop is. The project has recorded an append-only `order_events` trail since Phase 1, including the actor and timestamp of every transition. There is no real customer history on this installation, however, and a model trained or endorsed on invented activity would be portfolio theatre rather than engineering.

The implementation plan said “ADR 011” for this memo. ADR 011 already records the MinIO image decision, so this memo uses the next free number, 033.

## Decision

Estimate one narrow quantity: **the time a hypothetical new arrival might wait from entering a shop's queue until the shop starts printing it**. It is not a promised start or ready time for an order already on the order page.

For each shop, measure minutes per print unit (`pages × copies`) from the first `PRINTING` event to the first `READY` event. Use the most recent 50 valid durations. The estimate is the shop's current unfinished units multiplied by the 25th, 50th and 75th percentile speeds. Fewer than 10 samples uses documented default quartiles and is always labelled **Rough**. An empty queue is 0–0 regardless of history.

Only `PAID`, `RESERVED`, `ACCEPTED` and `PRINTING` count as unfinished work. Cash reservations are included; unpaid and already-ready orders are excluded. A currently printing order counts at full size because there is no page-level progress signal, which is a conservative approximation. `READY`, not collection, completes a speed sample.

The p25–p75 interval is a heuristic speed range, **not a confidence interval**. No separate overhead is added: ordinary handling is already inside the PRINTING→READY duration, so adding it again could double count it.

The API exposes only the aggregate range, sample count, fallback flag and algorithm version. Shop lists receive it in their existing batched responses; the order page calls `GET /shops/{id}/wait-estimate`. There is no per-card request fan-out and no raw event or customer data in the response.

A deterministic `make seed-history` command creates clearly labelled simulated cash orders through the real create/transition services. `make backtest-estimates` replays the event trail walk-forward and writes `backend/estimate_backtest.json`. At each prediction it uses only queue state and speed samples available then. Its baseline is the expanding global mean of the same actual target, using only actual waits already known then. The unrounded median is scored with mean absolute error.

**ML is rejected.** The available dataset is simulated, small and generated by known rules. It cannot establish that a model generalises to real shops, vendor click behaviour, interruptions or changing demand. A candidate model would need a time-separated evaluation on enough real completed orders and a clear win over this baseline before the decision is revisited.

## Measured result

The committed report was generated from 90 simulated completed orders across the three demo shops. One first-order warm-up has no earlier actual for the baseline, leaving 89 evaluated orders.

| Scope | n | Rule MAE | Global-average MAE | Rule wins? |
|---|---:|---:|---:|---|
| Overall | 89 | 3.4140 min | 5.9899 min | Yes |
| Central Prints | 29 | 3.6644 min | 4.5344 min | Yes |
| Campus Copy Center | 30 | 3.8361 min | 5.9857 min | Yes |
| Quick Print House | 30 | 2.7500 min | 7.4012 min | Yes |

There were 29 predictions made with the rough fallback. The result validates the plumbing and provides a baseline comparison; it is not a production accuracy claim and is not evidence for ML.

## Alternatives considered

1. **A global average for every shop.** Retained as the naive baseline, not the product rule: it ignores the current queue and differences between shops.
2. **A single-point estimate.** Rejected: it suggests precision that sparse and noisy event data does not support. The range and Rough label communicate uncertainty without inventing a confidence level.
3. **A learned ETA model.** Rejected: there is no real labelled history or evidence that added complexity would beat the rule on held-out real data.
4. **Order-specific ready-time promises.** Rejected: a shop-only endpoint does not know a new order's options or future queue changes. The UI states the narrower measurand instead.
5. **A materialised statistics table.** Rejected for now: no measured latency problem justifies another stateful aggregate. The additive view and bounded queries are the smaller change.

## Consequences

- `order_service` uses one injected aware-UTC clock for order fields and every event, so historical simulation cannot create false durations.
- `order_print_durations` is an additive, reversible database view. No new statistics table is required.
- Statistics failure cannot hide the core shop list: batched responses omit the estimate and the UI says it is unavailable. Shop selection remains usable.
- The report must be regenerated when the algorithm or seed data changes. Real and simulated reports must never be presented as the same evidence.
- Real accuracy may be worse when vendors click Start or Ready late or in bursts. The accuracy report is the prompt to improve that workflow before considering a model.

## Revisit trigger

Reconsider only when there is enough consented real completed-order history for a time-separated evaluation, the rolling rule loses clearly to a candidate across shops and periods, and the operational cost of the candidate is justified. If timestamps are unreliable, fix the event workflow first.
